# Zum OK Lab Flensburg beitragen

Vielen Dank für dein Interesse an unseren Open-Source- und Open-Data-Projekten.

Beiträge sind in vielen Formen willkommen: Code, Daten, Dokumentation, Tests, Barrierefreiheit, UX/UI, Recherche, Übersetzungen und Fehlerberichte.

## Wo anfangen?

1. Wähle ein Repository aus unserer [Projektübersicht](https://github.com/orgs/oklabflensburg/repositories?type=public).
2. Prüfe vorhandene Issues und Pull Requests.
3. Suche nach [`good first issue`](https://github.com/search?q=org%3Aoklabflensburg+is%3Aissue+is%3Aopen+label%3A%22good+first+issue%22&type=issues) oder [`help wanted`](https://github.com/search?q=org%3Aoklabflensburg+is%3Aissue+is%3Aopen+label%3A%22help+wanted%22&type=issues).
4. Lies die projektspezifische `CONTRIBUTING.md`, falls das Repository eine eigene besitzt. Diese hat Vorrang vor diesem organisationsweiten Leitfaden.

## Bevor du eine größere Änderung beginnst

Bitte eröffne bei größeren Funktionen, Architekturänderungen, neuen Datenquellen oder umfangreichen Refactorings zuerst ein Issue. So können Ziel, Umfang und mögliche Auswirkungen gemeinsam geklärt werden, bevor viel Arbeit entsteht.

Kleine Fehlerbehebungen, Dokumentationskorrekturen oder klar abgegrenzte Verbesserungen können direkt als Pull Request vorgeschlagen werden.

## Gute Issues

Ein hilfreiches Issue beschreibt möglichst:

- das Problem oder die Idee,
- das erwartete Verhalten,
- das tatsächliche Verhalten bei Bugs,
- Schritte zum Reproduzieren,
- relevante Umgebung wie Browser oder Betriebssystem,
- Screenshots oder Beispieldaten, sofern sinnvoll und frei von sensiblen Informationen.

Sicherheitslücken gehören nicht in öffentliche Issues. Siehe dazu [SECURITY.md](SECURITY.md).

## Pull Requests

Ein guter Pull Request ist möglichst fokussiert und enthält:

- eine kurze Beschreibung von Problem und Lösung,
- einen Verweis auf ein zugehöriges Issue, falls vorhanden,
- Angaben zu ausgeführten Tests,
- Screenshots bei sichtbaren UI-Änderungen,
- Hinweise zu Datenmigrationen, Konfiguration oder Breaking Changes,
- aktualisierte Dokumentation, wenn sich Bedienung oder Schnittstellen ändern.

Bitte vermische unabhängige Änderungen nicht unnötig in einem Pull Request.

## Qualität und Tests

Nutze die im jeweiligen Repository dokumentierten Entwicklungs- und Testbefehle. Bestehende CI-Prüfungen sollten vor dem Merge erfolgreich sein.

Für neue oder geänderte Funktionen erwarten wir passende Tests, soweit dies im jeweiligen Projekt sinnvoll ist.

## Daten und Datenschutz

- Committe keine Zugangsdaten, API-Schlüssel oder privaten Schlüssel.
- Veröffentliche keine personenbezogenen oder nicht öffentlichen Daten.
- Dokumentiere Herkunft und Lizenz neuer Datensätze.
- Achte bei OpenStreetMap- und Verwaltungsdaten auf die jeweiligen Lizenz- und Quellenangaben.

## Barrierefreiheit und Sprache

Öffentliche Anwendungen sollen möglichst verständlich, tastaturbedienbar und barrierearm sein. Achte bei UI-Änderungen auf semantisches HTML, sichtbare Fokuszustände, ausreichende Kontraste und verständliche Beschriftungen.

Viele unserer Anwendungen richten sich primär an deutschsprachige Nutzerinnen und Nutzer. Technische Bezeichner und Code dürfen englisch sein. Projektspezifische Regeln haben Vorrang.

## Zusammenarbeit

Wir arbeiten ehrenamtlich. Reviews und Antworten können daher etwas Zeit benötigen. Sachliches Feedback, nachvollziehbare Änderungen und kleine, gut prüfbare Pull Requests erleichtern die Zusammenarbeit erheblich.

Mit deinem Beitrag bestätigst du, dass du die eingereichten Inhalte selbst erstellt hast oder zu ihrer Weitergabe unter der Lizenz des jeweiligen Projekts berechtigt bist.
